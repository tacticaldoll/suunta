## Context

`suunta-contract`'s types split into two families: body-free reading types
(`Fix`, `Sounding`, `SatisfactionFinding`, `CoverageFinding`) that never carry a
domain payload, and `Body`-generic value types (`Correction<Body>`, `Course<Body>`,
`Bearing<Body>`, `Residual<Body>`) that do. Six other non-generic types (`Sigil`,
`Reversibility`, `Satisfaction`, `InFlightIndex`, `CoverageEffect`,
`SurfacedFinding`) already derive `PartialEq`/`Eq`. The eight types above do not,
though nothing in their content resists it.

## Goals / Non-Goals

**Goals:**
- Let a consumer compare these values directly (`==`, `assert_eq!`) instead of
  destructuring every field by hand.
- Keep the change purely additive and non-breaking.
- Add no bound to any core-owned function; the core's own operations must stay
  exactly as unconstrained as they are today.

**Non-Goals:**
- `Hash` or `Ord` derives. No use case was identified for putting these types in
  a `HashSet`/`HashMap`/`BTreeSet`; adding them speculatively would be scope
  creep beyond the identified gap.
- Any change to `Correction`, `Course`, `Bearing`, or `Residual`'s own methods,
  fields, or construction.

## Decisions

- **Derive `PartialEq, Eq` unconditionally on the four body-free types.** Every
  field they hold (`Sigil`, `Satisfaction`, `InFlightIndex`, `CoverageEffect`, and
  `Vec`s thereof) already implements both, so the derive costs nothing and adds
  no new bound anywhere.
- **Derive `PartialEq` (and `Eq` where valid) conditionally on the four
  `Body`-generic types.** Rust's derive macro generates a bound scoped to the
  derived impl itself (`impl<Body: PartialEq> PartialEq for Correction<Body>`),
  not to the type's inherent methods. `Correction::new`, `.sigil()`, `.body()`,
  and every other core-owned function keep their existing signatures, unchanged
  and unbounded. A consumer whose `Body` does not implement `PartialEq` loses
  nothing it has today; a consumer whose `Body` does gains the ability to
  compare.
- **This does not touch "no core-imposed trait bound on `Body`."** That
  requirement (see "A Correction Carries An Opaque Domain Payload") is about the
  core's own operations never requiring or reading a `Body` capability. A derived,
  conditional trait impl invoked only by the consumer's own code is a different
  axis: it adds a capability *if the consumer's type already has it*, and reads
  nothing through it — equality is structural field comparison, generated by the
  compiler, not a core-authored comparison of meaning (the same class of
  precedent already established for `Sigil`: "the core compares bytes, not
  meaning").

## Risks / Trade-offs

- [Risk] A future `Body` that only implements `PartialEq` incorrectly (e.g. a
  non-reflexive impl) would make `Correction<Body>` equality behave
  inconsistently. → Mitigation: this is entirely the consumer's own `Body` impl;
  the core neither authors nor audits it, exactly as it already doesn't audit any
  other property of `Body`.
- [Risk] Someone reads "the core makes no semantic judgment" and assumes adding
  `PartialEq` anywhere is suspect. → Mitigation: this design's Decisions section
  states explicitly why a derived, conditional structural-equality impl is not a
  semantic judgment (no core-authored comparison of meaning, no core-owned
  function gains a bound), and the delta spec's scenario makes this a checkable
  claim.
